## Context

Four independent implementation gaps, all discovered during the now-archived `mp-od-prototype-alignment` engagement and parked in its legacy-issues list because they were out of that change's screen-alignment scope. Each has already been root-caused down to the exact file/line during this change's proposal research (see below) — this design records the confirmed current state and the chosen fix per gap, not open investigation.

### Gap 1: Cart item update/toggle endpoints (404)
`frontend/src/features/cart/api.ts` already calls `PUT /api/cart/items/{productId}` and `PATCH /api/cart/items/{productId}`, but `com.seafood.order.api.CartController` only has `GET /`, `POST /items`, `DELETE /items/{productId}`, `DELETE /`. The domain aggregate is otherwise ready: `CartItem.selected` and `Cart.requireNonEmptySelected()` already exist and are already consumed by `CartService#enrich` — only the two mutation methods and their Controller routes are missing.

### Gap 2: Direct-buy order creation touches the cart
`mini-program` spec's "Direct buy from product detail" requirement already mandates mp-06 (order-confirm) "MUST NOT touch the cart store" for a direct-buy entry. `OrderController#create` / `OrderService#create(userId, paymentMethod)` today unconditionally load `Cart` by `userId`, requiring a non-empty cart — there is no way to pass explicit items. mp-03's "立即购买" currently approximates this by calling `cartStore.addItem()` then navigating to checkout, which is a real spec violation (it does touch the cart).

### Gap 3: Address `district` field
`openspec/specs/address-management/spec.md:17` already requires `district` as its own field. `com.seafood.user.domain.Address` only has `province/city/detail`. The gap was worked around, not fixed: `AddressUpsertRequest` (the mp-facing request DTO) already accepts `district` from the three-level region picker and explicitly documents folding it into `detail` as a **lossy** workaround ("回读 edit 页地区选择器无法回填 district"). `frontend/pages-sub/user/address/address-edit.js` already reads/writes `address.district` end-to-end (line 49, 65, 128) expecting the backend to round-trip it — it never has, because the backend has nowhere to store it separately.

### Gap 4: Legacy token bridge on cold start
`frontend/app.js#checkLoginStatus` reads `wx.getStorageSync('token')` — a storage key the current auth stack (`frontend/src/features/auth/store.ts` / `.js`, via `tokenStorage` in `src/shared/api/storage.ts`) never writes (it writes `accessToken`/`refreshToken`). `frontend/utils/request.js` only attaches `Authorization` when `app.globalData.token` is truthy (line 28). Net effect: on a cold start where the user is already logged in from a previous session (no new `login()` call fires), `globalData.token` stays unset, and any code still calling the legacy `utils/request.js` for an authenticated request silently sends no bearer token. Confirmed current impact: mp-04 cart default-address auto-select, mp-06 order-confirm default-address auto-select.

## Goals / Non-Goals

**Goals:**
- Close all 4 gaps so the already-approved specs (`backend-api`, `address-management`, `mini-program`) match what the code actually does
- No behavior change for existing callers that don't use the new capabilities (backward compatible: `items` on `POST /api/orders` is optional, `district` is a new optional-looking field that doesn't break existing address flows)

**Non-Goals:**
- SKU-aware cart/order lines. Neither `CartItem` nor `OrderItem` carries `skuId` today; a multi-SKU product added to cart already loses which SKU was picked, independent of this change. Direct-buy `items` here is `{productId, quantity}` only — extending SKU-awareness into cart/order is a separate, larger change (flagged as a new legacy issue in proposal.md's Impact section)
- Full legacy `utils/request.js` retirement, or auditing every other page still using it. This change only bridges `globalData.token` at `onLaunch` so the *existing* legacy-request-layer callers stop silently failing; it does not migrate them to the new request layer
- Backfilling `district` on existing address documents beyond what MongoDB's schemaless read tolerates (see Migration Plan) — no data migration script, no admin bulk-edit tool
- User domain membership fields, mp-07 address-card layout, cross-screen naming cleanup — each is its own change (see proposal.md Impact)

## Decisions

### D1: Cart mutation semantics — 404 on unknown line, not silent no-op
`removeItem` today silently no-ops if the productId isn't in the cart (filters it out either way). For `updateQuantity`/`toggleSelected`, a request against a path-scoped resource that doesn't exist is chosen to return HTTP 404 `code=NOT_FOUND` instead of silently no-op-succeeding, because these are read-modify-write operations on a specific line (unlike delete, which is idempotent-by-design) — a 200 response implying "your quantity update was applied" when nothing existed to update would be misleading to the frontend's optimistic-update UI. `Cart.updateQuantity(productId, quantity)` / `Cart.toggleSelected(productId)` throw a new `DomainException`-adjacent lookup failure that the Service layer translates to `NotFoundException` (existing `com.seafood.shared.error.NotFoundException` → 404, consistent with the `AddressController#get` pattern).

Alternative considered: silently no-op like `removeItem`. Rejected — masks real client bugs (stale productId from a race with another tab/device) the same way the `err.status`/`err.statusCode` mismatch from the prior engagement did.

### D2: Quantity update replaces, does not add
`PUT /api/cart/items/{productId}` with `{quantity}` sets the line to that exact quantity (mirrors `AddAddressRequest`-style full-replace PUT semantics elsewhere in this codebase), distinct from `POST /api/cart/items` which merges/adds. This matches the frontend contract comment already in `cart/api.ts` ("update {quantity}") and the mp stepper UI's actual usage (send the new absolute count after +/-, not a delta).

### D3: Direct-buy order creation — new optional `items` field, same validation pipeline
`CreateOrderRequest` (new DTO, replaces the current no-body `create()`): `{ items: List<CartItemRequest> | null }`. `OrderService#create` branches: `items` non-null/non-empty → build the `OrderItem` list directly from the request (reusing the exact same per-line existence/status/stock checks and `productDecrementOrThrow` loop as the cart path — extracted into a shared private helper so both paths share one validation implementation, not two copies of the "商品不存在/已下架/库存不足" logic); `items` null/empty → unchanged existing cart-read path. Neither path is allowed to touch the *other* data source (cart path never reads request items; direct-buy path never reads or clears the cart).

Alternative considered: a separate `POST /api/orders/direct-buy` endpoint. Rejected — `mini-program` spec frames this as the same `POST /api/orders` call from the frontend's perspective ("all respects except the source of the line items"); a second endpoint would need to duplicate the entire response shape and permission model for no benefit.

### D3b: mp-03 → mp-06 item hand-off — URL query, not cross-page instance stash

**Correction found during Task 2 research (post-approval, pre-implementation):** the original tasks.md wording for this gap ("mp-03 直接调用 `OrderAPI.create`") was wrong — it would skip mp-06 (order-confirm) entirely, losing address selection / shipping method / remark for direct-buy orders. The `mini-program` spec is explicit that direct-buy still "proceeds directly to the order confirmation screen (mp-06)" with items pre-loaded — mp-06 remains the place order creation actually happens; only the *source* of its line items changes.

Current `onBuyNow` (`frontend/pages-sub/product/product-detail/product-detail.js:143-166`) calls `cartStore.addItem()` then `wx.navigateTo(...order-confirm?source=direct_buy)`; `order-confirm.js`'s `onLoad` (line 66-76) never actually reads `options.source` today — it unconditionally calls `refreshCartPreview()` (reads the full cart). Both need to change:

- `onBuyNow`: stop calling `cartStore.addItem()`. Build `items = [{ productId: product.id, quantity: this.data.quantity || 1 }]` and navigate to `` `/pages-sub/order/order-confirm/order-confirm?source=direct_buy&items=${encodeURIComponent(JSON.stringify(items))}` ``. Chosen over the existing `getCurrentPages()` / `prevPage.xxx = value` cross-page-stash pattern (used elsewhere for address-list → order-confirm) because that pattern only works for *backward* navigation (`navigateBack` onto an already-existing page instance) — here mp-06's page instance doesn't exist yet at the point mp-03 calls `navigateTo`. URL query is the standard mp mechanism for forward hand-off; the payload is one line item, safely small for a query string. **This is not a novel pattern for this file** — `order-confirm.js#selectAddress` (line ~177-189) already does exactly this: `encodeURIComponent(JSON.stringify(selectedAddress))` in a `navigateTo` URL, for the same "forward hand-off of one small object" reason. Follow that precedent's exact style.
- `order-confirm.js#onLoad`: branch on `options.source === 'direct_buy'` — if so, parse `JSON.parse(decodeURIComponent(options.items))` and render the order preview from those items directly (map into the same `{id, name, price, quantity, imageUrl}` shape `refreshCartPreview` already builds — product name/price/image need an extra `ProductAPI.get(productId)` call per line since the URL only carries `productId`+`quantity`, not display fields); skip `cartStore.refresh()` entirely for this branch. Otherwise (no `source` or a different value): existing `refreshCartPreview()` path, unchanged. (Enrichment call is `ProductAPI.getById(productId)`, not `.get()` — verified against `src/features/product/api.ts:23`.) **Must populate `this.data.cartItems` in that exact shape and call `this.recalcAmounts()`** — `recalcAmounts()` (line ~167-175) reads from `this.data.cartItems`, not `this.data.order.items`, to compute `subtotal`/`shippingFee`/`discount`/`orderTotal`/`itemCount`; this is the same data path `refreshCartPreview` feeds, so the direct-buy branch must feed the same field or the amount summary silently shows zeros.
- `order-confirm.js#onSubmitOrder`: needs a way to know it's in direct-buy mode (store the parsed `items` in page data during `onLoad`, e.g. `this.setData({ directBuyItems: items })`) and call a variant that (a) sends `{ items: directBuyItems, addressId, remark }` instead of `{ addressId, remark }`, and (b) does **not** call `cartStore.clear()` afterward (the cart was never touched, so there's nothing to clear — `orderStore.placeOrder()`'s existing best-effort `cartStore.clear()` call, `src/features/order/store.ts:76-80`, must be skipped for this path). Add a second `orderStore` method (e.g. `placeDirectBuyOrder(body)`) that calls `OrderAPI.create(body)` without the cart-clear side effect, rather than adding an `if` branch inside `placeOrder` that changes its behavior for existing callers.

### D4: Address `district` — additive field, no fold-back removal surprise
Add `district` as a new record component on `Address` (position: after `city`, before `detail`, matching the spec's field order) and on `AddAddressRequest`/`UpdateAddressRequest`. `AddressUpsertRequest.toAddRequest()`/`toUpdateRequest()` stop folding `district` into `detail` and instead pass `district` straight through; `detailAddress` (the mp field name) maps to the domain's `detail` (unchanged, still no fold). This is purely additive to the wire format — old clients not sending `district` get `district=null|""`, which existing scenarios (list/cart rendering) already tolerate today as an undefined interpolation (Java record component defaults to `null` when absent from Mongo BSON on read; validation requires `district` `@NotBlank` only on new writes going forward via `AddressUpsertRequest`, not retroactively on stored documents).

### D5: Token bridge — read at `onLaunch`, no network round-trip
Legacy `checkLoginStatus()`'s network-validate-then-set-`globalData.token` flow is replaced with a direct, synchronous bridge: `app.globalData.token = tokenStorage.getAccessToken()` (via the same `require('./src/shared/api/request.js')`-guarded try/catch pattern the file already uses two lines above for `setBaseUrl`, since the new request layer is what actually owns `tokenStorage`). No network call needed — an invalid/expired token surfaces the same way it already does today for any authenticated call (401 → existing silent-relogin path in `authStore`), this bridge only ensures the token that *is* present gets attached at all.

Alternative considered: keep `checkLoginStatus()`'s network validation and fix its storage key from `token` to `accessToken`. Rejected — `/auth/me` is not a real endpoint in the current backend contract (confirmed against `auth` spec and `UserController`); the legacy method was already dead-in-practice beyond the side effect of setting `globalData.token`, so replacing it outright is less code than fixing a call to a nonexistent endpoint.

## Risks / Trade-offs

- [Risk] Extracting a shared order-item-validation helper touches `OrderService#create`, a method already flagged in the prior engagement's legacy-issues list as duplicated logic elsewhere (`order-list.js`/`order-detail.js`) → Mitigation: this is backend Java, unrelated to that frontend duplication; scoped strictly to the two order-creation paths introduced by this change, not a general refactor of `OrderService`
- [Risk] 404-on-unknown-line (D1) is a judgment call, not dictated by an existing pattern elsewhere in `CartController` → Mitigation: documented explicitly in the delta spec scenarios so it's testable and reviewable, not an implicit assumption
- [Risk] `district` field addition changes `Address`'s constructor arity (record with positional args) → Mitigation: `Address` is only constructed in `UserService` (2 call sites) and via Mongo deserialization; both call sites are within this change's Impact and will be updated together, `./gradlew test` will fail loudly at compile time for any missed call site (record constructor mismatch is a compile error, not a runtime surprise)

## Migration Plan

- No explicit Mongo migration script. Spring Data MongoDB's record-based converter supplies `null` for a `String` record component whose BSON key is absent — existing address subdocuments without `district` deserialize with `district = null` and render as an empty segment in `province+city+district+detail` interpolation (same as today's `detailAddress` gap, just narrowed to one field instead of two). Users who edit an existing pre-migration address will have `district` populated going forward once they save through the fixed `address-edit` flow.
- `backend/seed/fixtures/users.json`'s one seed address gets a `district` value added (`"陆家嘴街道"` or similar) as part of this change's tasks, so dev/C5-visual-verification data renders realistically post-fix.
- Rollback: reverting the 4 gaps' commits is safe independently of each other (no shared migration state, no BREAKING wire changes) — each gap's commit(s) can be reverted alone if a regression is found in only one.
